# ソースコードを書いてから、画面に結果が表示されるまで

ソースコードを書けば画面に結果が表示されるのは、紙の上で鉛筆を動かせば線ができるように当然のことだとおもっていましたが(最初はそこまで考えるよ余裕がなかった)、なぜ動くのかがふと気になることがありました。
そこで調べてみたところ、この疑問を解決してくれそうな有名な書籍があったので読んで学んだことを書こうと思います。

『プログラミングはなぜ動くのか　第3版』

この記事では、本書の章タイトルを軸にしながら、次の疑問を初心者向けに整理します。※「ソースコードから画面に表示されるまで」を今回書いているので一部の章を割愛しています。

> ソースコードを書いてから、画面に結果が表示されるまでに何が起きているのでしょうか？

たとえば、次のプログラムを実行するとします。

```python
message = "こんにちは"
print(message)
```

この2行が画面に文字を表示するまでの流れを、順番に見ていきます。

## 第1章｜プログラマにとってCPUとはなにか

この章では、プログラムを実際に実行するCPUの役割について考えます。

### CPUは命令を解釈して実行します

CPUは、メモリに置かれた命令を読み取り、内容を解釈し、実行する装置です。主に、次のような部分から構成されています。

| 部分 | 役割 |
| --- | --- |
| 制御装置 | 命令を解釈し、CPU内部の各部分に指示を出します |
| 演算装置 | 足し算や比較などの計算を行います |
| レジスタ | 命令や計算に使うデータを一時的に保存します |
| クロック | CPUが動作するタイミングを作ります |

CPUの処理を単純化すると、次の繰り返しになります。

```text
命令を読む → 命令を解釈する → 命令を実行する
```

### レジスタが処理を支えます

レジスタは、CPUがすぐに使うデータを一時的に保存する場所です。レジスタにはそれぞれ役割があります。

- **アキュムレータ**：演算に使うデータや、演算結果を保持します
- **プログラムカウンタ**：次に実行する命令のアドレスを保持します
- **命令レジスタ**：現在実行する命令を保持します
- **フラグレジスタ**：演算結果が正か、0か、負かなどの状態を保持します
- **汎用レジスタ**：一時的なデータを保持します
- **スタックレジスタ**：スタック領域の位置を管理します

特に重要なのがプログラムカウンタです。メモリには命令やデータがアドレスという番号付きの場所に置かれており、プログラムカウンタには次に読む命令のアドレスが入っています。

通常は、命令を実行すると次のアドレスへ進みます。しかし、`if` 文や `for` 文では、条件に応じて別の場所へ移動します。CPUは比較結果をフラグレジスタに保存し、その値を見てプログラムカウンタに別のアドレスを設定します。これがジャンプ命令です。

関数を呼び出すときは、呼び出し元へ戻るためのアドレスをスタックに保存してから、関数のあるアドレスへ移動します。関数の処理が終わると、保存しておいたアドレスを取り出して、元の処理へ戻ります。

## 第2章｜データを２進数でイメージしよう

この章では、コンピューターがなぜ0と1を使ってデータを扱うのかを考えます。

CPUやメモリを構成するICには、電気が流れているか、流れていないかを読み取る端子があります。この2つの状態を表現するのに、0と1からなる2進数が適しています。

文字、整数、画像、音声なども、コンピューター内部では最終的にビット列として保存されます。ただし、同じビット列でも、整数として扱うのか、文字として扱うのかによって意味は変わります。

### シフト演算

シフト演算は、ビット列を左右にずらす処理です。2進数を左へ1ビットずらすと、基本的には2倍になります。右へ1ビットずらすと、基本的には2で割った値になります。

```text
00000101（5）を左へ1ビット移動
00001010（10）
```

画面上のデータを移動させる処理や、2のべき乗の計算などに利用されます。

### 2の補数

コンピューターが負の整数を表現するときには、2の補数という方法が使われます。ビットを反転して1を加えることで、正の値と負の値を同じ加算回路で扱いやすくします。

また、ビット列を数値として扱うのか、単なる0と1の並びとして扱うのかによって、同じシフトでも意味が変わります。算術シフトでは数値としての符号を考慮し、論理シフトではビット列として扱います。

## 第3章｜コンピューターが小数点数の計算を間違える理由

この章では、コンピューターの計算結果に誤差が生じる理由を扱います。

2進数では、10進数の `0.1` のように正確に表現できない小数があります。2進数の小数は、`1/2`、`1/4`、`1/8` のような値の組み合わせで表現するためです。

表現できない値を有限のビット数に収めるには、どこかで値を丸めなければなりません。そのため、計算結果に誤差が生じることがあります。

### 浮動小数点数

コンピューターでは、小数を浮動小数点数という形式で保存することがあります。浮動小数点数では、数値を符号、仮数、指数などに分けます。

```text
数値 = 符号 × 仮数 × 基数の指数乗
```

小数点の位置を指数で表すことで、限られたビット数でも広い範囲の数値を扱えるようになります。しかし、浮動小数点数でもすべての小数を正確に保存できるわけではありません。

金額の計算など、誤差を避けたい場合には、整数に変換してから計算し、最後に小数へ戻す方法が使われることもあります。

## 第4章｜四角いメモリを丸く使う

この章では、メモリの構造と、メモリを効率的に使うためのデータ構造について考えます。

### メモリはアドレスで管理されます

メモリは、データを保存する場所が細かく分けられ、それぞれにアドレスが付けられています。CPUはアドレスを指定することで、目的のデータを読み書きします。

メモリには、データを保存するための端子だけでなく、アドレスを指定する端子や、読み書きを指定する端子、電源用の端子もあります。データ用の端子が8本あれば、1回に8ビット、つまり1バイトのデータを扱えます。

### 配列とポインタ

配列は、同じ種類のデータを連続した領域に並べて保存する仕組みです。配列の先頭アドレスを基準にし、そこから何番目の要素かという相対的な位置を使うことで、目的の要素を計算できます。

```text
先頭アドレス：1000
要素の位置　：3
要素の大きさ：4バイト

3番目の要素のアドレス
= 1000 + 3 × 4
= 1012
```

C言語のポインタは、データそのものではなく、データが置かれているアドレスを保存する変数です。ポインタの型によって、そこから何バイト分のデータを読み取るかが変わります。

### スタック、キュー、リング・バッファ

プログラムの実行中には、データを一時的に置くための領域も使われます。

- **スタック**：後入れ先出しでデータを管理します。関数の戻り先や一時的なデータの保存に使われます
- **キュー**：先入れ先出しでデータを管理します
- **リング・バッファ**：キューの末尾まで到達したら先頭へ戻るようにした構造です

リング・バッファを使うと、決められた範囲を繰り返し利用できます。データを一時的に順番に受け渡す処理などで利用されます。

## 第5章｜メモリーとディスクの親密な関係

この章では、プログラムを保存するディスクと、実行時に使うメモリの関係を見ていきます。

プログラムは、ディスクやSSDに保存されているだけではCPUがすぐに実行できません。実行時にはOSがプログラムをメモリへ読み込みます。

```text
ディスク・SSD：プログラムを保存しておく場所
メモリ　　　：実行中の命令やデータを置く場所
レジスタ　　：CPUがすぐに使う少量のデータを置く場所
```

ディスクは大量のデータを保存できますが、CPUが直接読み書きするには時間がかかります。そのため、よく使うデータをメモリに一時保存するディスクキャッシュが使われます。

また、ディスクの一部を仮想的なメモリとして扱う仮想記憶もあります。プログラムをページという単位に分け、必要なページをディスクからメモリへ読み込むことをページイン、使わなくなったページをディスクへ戻すことをページアウトといいます。

この仕組みにより、メモリ容量より大きなプログラムも実行できます。ただし、ディスクとの読み書きが増えるため、メモリだけで実行する場合より遅くなります。

SSDは、電源を切ってもデータが残る記憶装置であり、フラッシュメモリを使うため、HDDより高速に読み書きできます。

## 第7章｜プログラムはどんな環境で動くのか

この章では、プログラムがどのコンピューターでも同じように動くとは限らない理由を考えます。

プログラムが動作するかどうかは、コンピューターの性能だけでなく、OSやCPUの種類にも左右されます。OSやCPUが違えば、プログラムを実行するための命令や、ハードウェアとのやり取りの方法が異なるからです。

通常のコンパイラは、使用するOSやCPUに合わせたネイティブコードを作ります。そのため、Windows用に作られた実行ファイルを、何も変更せずに別のOSで実行できるとは限りません。

一方、Javaのように、いったんバイトコードへ変換し、そのバイトコードをJVMが各環境に合わせて実行する仕組みもあります。このような仕組みにより、OSの違いをある程度吸収できます。

## 第8章｜ソース・ファイルから実行可能ファイルができるまで

この章では、ソースコードが実行ファイルになるまでの過程を見ていきます。

```text
ソースファイル
    ↓ コンパイル
オブジェクトファイル
    ↓ リンク
実行可能ファイル
```

コンパイラは、ソースコードを機械語に近い形のオブジェクトファイルへ変換します。しかし、ソースコードで使っている標準関数やライブラリの処理内容まで、すべてがそのファイルに含まれているとは限りません。

そこで、コンパイルしたオブジェクトファイルと、必要なライブラリファイルやスタートアップファイルをリンクして、実行可能ファイルを作ります。

実行可能ファイルをメモリへ移すときには、関数や変数を実際のメモリアドレスに対応付ける必要があります。ファイル内で相対的な位置を使っておき、実行時に実際のアドレスへ置き換える処理を再配置といいます。

実行時には、スタックやヒープもメモリ上に用意されます。スタックは関数の呼び出しや一時的なデータに使われ、ヒープはプログラムが必要な大きさを指定して確保するデータに使われます。ヒープの解放を忘れると、メモリリークが発生します。

複数のプログラムで共通して使う関数をDLLなどの共有ライブラリにまとめると、同じ関数をそれぞれのプログラムに重複して持たせずに済みます。

## 第9章｜OSとアプリケーションの関係

この章では、OSがアプリケーションとハードウェアの間でどのような役割を果たしているのかを見ていきます。

OSは、複数のアプリケーションに共通する処理をまとめて提供しています。ファイルを開く、キーボードから入力を受け取る、画面に表示する、といった処理をアプリケーションがすべて自分で実装する必要はありません。

アプリケーションは、OSのAPIやシステムコールを通して処理を依頼します。OSはその依頼を受け、デバイスドライバなどを使って実際のハードウェアを操作します。

この仕組みがあるため、アプリケーションはハードウェアごとの細かな違いをすべて意識せずに済みます。GUI、ネットワーク、マルチタスクなどの機能も、OSが共通の仕組みとして提供しています。

コンピューターの電源を入れたときも、いきなりOSが動き始めるわけではありません。まずBIOSなどがハードウェアを確認し、ブートローダーがOSをメモリへ読み込んで起動します。

## 第11章｜ハードウェアを制御する方法

この章では、OSやCPUがキーボード、ディスプレイなどのハードウェアとどのようにやり取りするのかを見ていきます。

### 割り込み

ハードウェアは、プログラムが常に状態を確認し続けなくても、処理が必要になったことをCPUへ知らせられます。これが割り込みです。

たとえばキーボードから入力があったとき、CPUは実行中の処理を一時的に保存し、入力を処理するプログラムへ移ります。処理が終わると、保存しておいた状態を戻し、元の処理を再開します。

### DMAとGPU

大量のデータをハードウェアとメモリの間で移動させる場合には、CPUを介さずに転送するDMAが使われることもあります。

画面へ表示するデータは、ディスプレイ側のメモリであるVRAMに置かれます。動画やゲームのように大量の画像データを高速に処理する場合は、グラフィック処理に特化したGPUが使われます。

## ここまでの章をつなげると

### 画面に結果が表示されるまで

ここまでの章の内容を、最初のプログラムに当てはめて整理します。

```python
message = "こんにちは"
print(message)
```

1. ソースファイルがコンパイラやインタプリタに渡されます
2. 実行に必要な命令や文字データが用意されます
3. 必要なライブラリなどと結合され、実行できる形になります
4. OSがプログラムをメモリへ読み込みます
5. CPUがプログラムカウンタに従って命令を読みます
6. レジスタや演算装置を使って、必要なデータを処理します
7. プログラムがOSへ表示処理を依頼します
8. OSやデバイスドライバが表示装置へデータを渡します
9. ディスプレイがデータを画面に表示します

実際には、文字コード、ウィンドウ管理、描画用のバッファなど、さらに多くの仕組みが関わります。しかし、まずは次の流れをつかめれば十分です。

```text
ソースコード
  → コンパイラ・インタプリタ
  → メモリ
  → CPU
  → OS
  → ハードウェア
  → 画面
```

## まとめ

『プログラミングはなぜ動くのか』を読む前は、ソースコードを書けば、あとは何かが処理して画面に結果を表示してくれる、という程度の理解でした。しかし本書を読むことで、CPU、メモリ、ディスク、OS、コンパイラ、ハードウェアが、それぞれ異なる役割を担いながら連携していることがわかりました。

普段ソースコードを書くときに、CPUやメモリの動きを一つひとつ意識することはありません。それは、プログラミング言語やコンパイラ、OSが、複雑な処理の多くを私たちから隠してくれているからです。私たちは、その仕組みの上で、より人間に近い形でプログラムを書けます。

読む前は霧に包まれていた「ソースコードから画面表示まで」の流れが、読んでいくうちに、役割の異なる仕組みが連携してできているものとして見えるようになりました。このように複雑なものを役割ごとに分け、それぞれを連携させるという考え方は、ソフトウェアの設計にも通じると思います。

プログラムが動くということは、ソースコードが単独で何かを起こすことではありません。ソースコードを命令へ変換する仕組み、命令を実行するCPU、データを保持するメモリやディスク、そしてハードウェアを仲介するOSが、それぞれの役割を受け持っているからこそ、最終的に画面へ結果を表示できるのです。
